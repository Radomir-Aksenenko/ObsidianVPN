# Улучшения протокола Obsidian, 10 ноября 2026

Разбор ядра на коммите `9b37479` (ветка `main`). Правило отбора одно: ни одно
предложение не ослабляет маскировку или криптографию. Где улучшение скорости
задевает маскировку, оно либо выброшено, либо помечено отдельно.

Все тесты Windows и Linux (бинарники тестов запускались в WSL) проходят,
`go vet ./...` чистый, сборка для linux/amd64, linux/arm64, android/arm64,
darwin/arm64 проходит. Пункт 6 (recvmmsg) не сделан: он ускоряет только прямой
UDP, который выключен по умолчанию.

**Как работает rekey.** Клиент раз в 30 минут (±20%) делает внутри туннеля новый
обмен X25519 + ML-KEM-768 (сообщения INIT, RESP, FIN). Ключи новой эпохи
выводятся из свежих секретов и старого chain key. Каждое направление
переключается сразу после своего кадра-маркера под блокировкой отправки, поэтому
кадры двух эпох не перемешиваются и данные не теряются. UDP идёт следом: сервер
принимает новую эпоху до RESP и шлёт старой до FIN, клиент переключается после
RESP; предыдущая эпоха отбрасывается через 30 секунд. Утечка ключей сессии
перестаёт работать после следующей эпохи (post-compromise security). Лимиты
времени и пакетов сессии теперь считаются от последнего rekey.

**Совместимость сохранена**, хотя её можно было отбросить: сервер объявляет
поддержку зашифрованным кадром NOISE в случайный момент первых пяти минут,
старые клиенты его выбрасывают. Клиент начинает rekey только после объявления.
Rekey включается, только когда обновлены и сервер, и клиент; смешанные версии
работают как раньше, с обрывом через 6 часов.

Не проверено: race detector (нет cgo), реальная сеть и телефоны, сквозной тест
движка клиента с интервалом 30 минут по умолчанию (хуки проверены только в
модульных тестах). Один раз за время работы полный прогон пакета `obsidian` упал,
и в повторных прогонах (больше 40) это не воспроизвелось; причина не установлена.

`BenchmarkTunnelSend`, Windows amd64, Ryzen 5 7600X, loopback, 32 пакета по
1380 байт, три прогона. Старый путь клиента соответствует `SendData`, новый `SendDataBatch`:

| Режим | По пакету, МБ/с | Пачкой, МБ/с |
| --- | --- | --- |
| Сырой TCP | 96-127 | 1113-1122 |
| v5 records | 91-94 | 927-937 |

Это стоимость отправителя при полной очереди, а не скорость через интернет.
Одиночный пакет идёт как раньше, выигрыш появляется только когда в TUN уже
лежат несколько пакетов (загрузки, отдача, плотный поток ACK). Лишний переход
через канал между горутинами в этом замере не учтён. Что не проверено: реальная
сеть, телефоны, ARM VPS, захваты трафика для оценки маскировки.

Ниже исходный разбор.

Ничего из ниже перечисленного не доказывает и не опровергает поведение ТСПУ.
Эффект на маскировку здесь везде гипотеза, которую нужно мерить захватами.

## Что уже сделано хорошо

Чтобы не переделывать работающее:

- Гибридный обмен X25519 + ML-KEM-768, ключи сессии выводятся из обоих секретов,
  эфемерные публичные ключи входят в HKDF info. Сервер доказывает владение
  статическим ключом, клиент тоже.
- UDP: anti-replay проверяется после AEAD (`udp.go:639`, `udp.go:1020`), подделкой
  счётчика окно не сдвинуть. Маска RouteTag выводится из секретного credential.
- v5 records шифрует весь поток, включая ML-KEM рукопожатие; неявного downgrade нет.
- Native REALITY: настоящий TLS 1.3 через Xray, прямой UDP по умолчанию выключен.
- Служебные события (keepalive, recovery probes) уже рандомизированы без задержки DATA.

## 1. v5 records: менять ключ на лету, а не рвать сессию

**Что сейчас.** `reality_record_cipher.go:17` ограничивает каждое направление
`1 << 24` записями, `reality_records.go:178` после этого возвращает ошибку.
Клиент отправляет каждый пакет из TUN отдельным `SendData`
(`client/engine.go:789`, `:797`, `:861`), то есть одна TLS-запись на пакет.
Во время большой загрузки клиент шлёт TCP ACK примерно на каждые два пакета данных.
При 100 Мбит/с это около 4500 записей в секунду на uplink, лимит наступает
примерно через час. Дальше `tunnel send` падает, сессия рвётся, движок
переподключается с backoff (`client/engine.go:268`). Пользователь видит
подвисание загрузки на время нового рукопожатия ML-KEM.

**Что сделать.** На счётчике `1 << 24` обе стороны выводят новый ключ AES-GCM
через HKDF от старого (метка вроде `obsidian_reality_v5_record_update`),
обнуляют счётчик и забывают старый ключ. Это аналог TLS 1.3 KeyUpdate, только
детерминированный по счётчику, без нового сообщения.

**Совместимость.** Точка смены совпадает с точкой, где старый код сейчас
падает. Новый с новым продолжают работу. Новый со старым падают ровно там же,
где падают сегодня. Формат на проводе не меняется.

**Маскировка и защита.** На проводе ничего не меняется. Граница использования
одного ключа остаётся прежней (2^24 записей на ключ), так что запас по
стойкости AES-GCM тот же. Плюс прямая секретность внутри сессии: утечка
текущего ключа не раскрывает ранее записанные эпохи.

Native REALITY этот код не использует, там TLS ведёт uTLS/Xray.

**Проверка.** Тест с искусственно маленьким лимитом: запись через границу,
чтение через границу, отказ при рассинхроне, старый пир падает в той же точке.

## 2. Пачки пакетов на uplink клиента

**Что сейчас.** Сервер уже шлёт downlink пачками (`SendDataBatch`,
`cmd/server/main.go:581`, лимит 64 КиБ). Клиент читает TUN по одному пакету и
на каждый делает `SendData`: отдельный кадр, отдельная TLS-запись (в v5 и
native), отдельный системный вызов `write`. Прямой UDP у клиента тоже уходит
по одному `sendto` на пакет.

**Что сделать.** Отдельная горутина читает TUN и кладёт пакеты в канал.
Отправитель берёт первый пакет блокирующе, затем без ожидания забирает всё,
что уже лежит в канале (до 64 КиБ или 32 пакетов), и отдаёт одним
`SendDataBatch`. Таймеров нет, одиночный пакет уходит сразу, задержка не растёт.

- Windows: `tun_windows.go:36` уже умеет неблокирующий `ReceivePacket`,
  возвращающий `ERROR_NO_MORE_ITEMS`. Можно вычерпывать кольцо wintun напрямую,
  даже без лишней горутины.
- Linux, Android, iOS (fd/PacketDevice): вариант с горутиной и каналом.
  Позже можно добавить `IFF_VNET_HDR` и GRO на TUN, сейчас его нет нигде в коде.

**Выигрыш.** Меньше системных вызовов и AES-GCM вызовов на байт, меньше
заголовков TLS (по 22 байта на запись). Особенно заметно на телефонах и слабых
ПК при отдаче и при плотном потоке ACK. Счётчик записей из п. 1 растёт в разы медленнее.

**Маскировка.** Сейчас размеры TLS-записей от клиента один к одному повторяют
размеры вложенных IP-пакетов, это удобный признак. Браузер при отдаче пишет
крупные записи. Пачки разрывают эту связь. Это гипотеза, её нужно подтвердить
сравнением захватов, но ухудшения тут быть не может: содержимое и шифрование те же.

**Проверка.** Существующий `BenchmarkTunnelRoundTrip` плюс замер на ARM и
Android; проверить p50/p95 задержки для одиночных пакетов, она не должна вырасти.

## 3. Replay-кэш рукопожатия обходится сменой одного байта паддинга

**Что сейчас.** `cmd/server/main.go:619` считает ключ кэша как HMAC от всего
hello. Но pre-padding и паддинг S1 ничем не аутентифицированы:
`ProcessClientHello` их просто пропускает, а тег hello-кадра покрывает только
nonce. Достаточно перевернуть любой байт в хвосте S1, и повтор пройдёт мимо
кэша. В окне ±30 с сервер ответит настоящим ServerHello. Ключей атакующий не
получит, но получит подтверждение, что на порту Obsidian (активное зондирование).

**Где это важно.** Только там, где наблюдатель видит внутренний hello: legacy и
masked REALITY, обычный TCP. В v5 и native hello внутри шифрования, а повтор
всего потока ловит кэш SessionID REALITY.

**Что сделать.** Ключ кэша брать из `client_ephemeral_pub ‖ salt` (оба входят в
вывод ключей, их не подменить без поломки расшифровки). Это изменение только
сервера, клиент обновлять не нужно. Тест: повтор с одним изменённым байтом
паддинга должен отклоняться.

## 4. Паддинг вложенных TLS-рукопожатий

**Проблема.** Даже внутри настоящего TLS видно, как вложенный трафик меняет
размеры и направления записей. Рукопожатие TLS пользователя внутри туннеля
(ClientHello, ответ сервера с сертификатами) даёт узнаваемую последовательность.
Именно этот признак разбирает работа Xue и соавторов «Fingerprinting Obfuscated
Proxy Traffic with Encapsulated TLS Handshakes» (USENIX Security 2024). Xray
Vision борется с тем же.

**Что сделать.** Для первых нескольких пакетов каждого нового вложенного
TCP-потока (или для пакетов, похожих на TLS handshake по первому байту полезной
нагрузки) добавлять случайный паддинг и при необходимости кадр Noise.
Ограничить бюджетом: например, не больше 2 КиБ на поток и не больше 1-2% трафика.
Bulk-данные не трогать.

**Совместимость.** Поле PAD_LEN и пакет Noise уже есть в формате, получатель их
отбрасывает. Значит, менять нужно только отправителя, протокол не ломается.
Поле PAD_LEN однобайтовое, поэтому больше 255 байт на кадр добирать кадрами Noise.

**Цена.** Немного трафика на старте каждого соединения. На скорость bulk не влияет.

## 5. Настоящий rekey внутри туннеля

**Что сейчас.** `DeriveNextEpochKeys` (`crypto.go:378`) и оба `RatchetEpoch`
(`udp.go:433`, `udp.go:889`) нигде в рабочем коде не вызываются. Rekey фактически
нет. Вместо него сессия принудительно закрывается через 6 часов
(`obfuscation.go:82`, проверка в `obfuscation.go:511`), с тем же подвисанием, что в п. 1.

**Что сделать.** Новый тип служебного пакета с новым X25519 + ML-KEM обменом
внутри уже установленного туннеля, раз в час или по объёму. Ключи меняются по
эпохам, старая эпоха живёт короткое окно для пакетов в пути (для UDP механизм
prevTag уже есть). Это даёт post-compromise security: утечка ключей сессии
перестаёт раскрывать будущий трафик. Хэш-храповик без нового DH этого не даёт.

**Совместимость.** Сейчас неизвестный тип пакета рвёт туннель
(`typeIDToPacketType` возвращает ошибку, `recvLoop` выходит). Поэтому нужен
флаг возможности в рукопожатии, и только при нём слать rekey. Объём самый большой
в списке. После него лимит 6 часов можно убрать или сильно увеличить.

## 6. Пакетный приём UDP на сервере

`udp.go:967`: сервер читает по одной датаграмме на системный вызов
(`ReadFromUDPAddrPort`). На Linux можно читать пачками через `recvmmsg`
(`ipv4/ipv6.PacketConn.ReadBatch`) и включить `UDP_GRO`. Отправка с GSO уже есть.
Клиенту симметрично нужен `sendmmsg` (см. п. 2). Это ускоряет только прямой UDP,
а он в native REALITY по умолчанию выключен. Поэтому приоритет ниже.

## 7. Окно рассинхрона часов

`handshake.go:36`: окно ±30 секунд. Телефоны и ПК с уехавшими часами получают
отказ `replay/clock skew` без понятной причины. После п. 3 окно можно расширить
до 60 секунд: TTL кэша 2 минуты (`cmd/server/main.go:90`), он должен быть не
меньше удвоенного окна. Изменение только сервера. Клиенту стоит показывать
понятную ошибку про время.

## 8. Мелочи

- `transport.go:441`: в режиме обычного TLS при пустом fingerprint берётся
  `HelloChrome_120`, отпечаток 2023 года. Везде остальное уже `HelloChrome_Auto`.
  Заменить. Это затрагивает только вызовы библиотеки без явного fingerprint.
- `protocol.go:525`: если буфер меньше полезной нагрузки, `ParseFrameInto`
  копирует обрезанные данные, но возвращает полную длину. Текущие вызовы туда не
  попадают (буфер берётся по размеру кадра), но это мина: надо возвращать
  `io.ErrShortBuffer`.
- В `ProcessClientHello`/`ProcessServerHello` эфемерный ключ обнуляется только при
  успехе. На путях ошибки тоже стоит вызывать `Zero()`.

## Что сознательно не предлагаю

- **Убрать внутреннюю защиту заголовков и маску длины кадра в native REALITY.**
  На проводе их не видно, TLS всё скрывает, и это дало бы несколько процентов
  CPU. Но это минус слой защиты: при проблеме во внешнем слое метаданные туннеля
  откроются. По правилу «не ослаблять» отказываюсь.
- **Менять комбинатор X25519 + ML-KEM.** Эфемерные ключи X25519 уже в HKDF info,
  это совпадает с логикой X-Wing. Слабого места тут нет.
- **Менять внутренний шифр на AES-GCM ради скорости.** На ПК loopback уже около
  500 МБ/с, узкое место в WAN другое: системные вызовы на пакет, head-of-line
  blocking TCP и переподключения. Без замеров на ARM и телефонах это не обосновано,
  а ChaCha20 на слабых устройствах без AES-инструкций как раз быстрее.
- **Микрооптимизация создания ChaCha20 для заголовка на каждый пакет.** Пока нет
  замера, который показывает заметный выигрыш.
- **Включать прямой UDP по умолчанию.** Случайные байты по UDP без рукопожатия
  легко выделить; текущий выбор «выключено» правильный.

## Как проверять

Для каждого пункта: тесты в пакете, `go vet ./...`, бенчмарки до и после на той
же машине, отдельно ARM/Android. Для пп. 2 и 4: захваты трафика до и после и
сравнение распределений размеров TLS-записей. Утверждать, что ТСПУ стал хуже
распознавать протокол, можно только после полевой проверки из нескольких
российских сетей, описанной в `reports/Маскировка и скорость Obsidian.md`.
