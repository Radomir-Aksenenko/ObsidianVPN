# Obsidian: native REALITY, 9 ноября 2026

Реализован дополнительный транспорт `native-reality`: поддерживаемый TLS 1.3
через Xray v26.11.9 / REALITY вместо самостоятельно собранного внешнего TLS
flight. Внутренний Obsidian с ML-KEM и существующей аутентификацией сохранён.
Это локальная реализация с функциональными проверками, а не подтверждение
нераспознаваемости ТСПУ или доступности из России.

## Поведение

- Клиент завершает и проверяет настоящий upstream REALITY TLS handshake до
  отправки внутреннего hello. ClientHello использует upstream fingerprint
  `chrome`; Android/iOS socket protection вызывается до подключения.
- Обычный неавторизованный TLS-клиент попадает на настоящий сайт прикрытия.
  Неправильный short ID не возвращает рабочий Obsidian-туннель.
- Отключены неявные переходы native → v5/raw и автоматический прямой UDP.
  Даже `enable_udp_data:true` не разрешает обход TLS без `allow_direct_udp:true`.
- Сервер ограничивает одновременно ожидающие рукопожатия (128) и время
  каждого (12 с). Инициализация шаблона цели ограничена 12 с. Отмена listener
  закрывает ожидающие sockets; смена сети/Stop отменяет клиентский handshake.
- Важно сохранить upstream server setting `SessionTicketsDisabled:true`:
  REALITY самостоятельно зеркалит ticket records цели. Обычная генерация
  tickets поверх этого вызывает ошибку уже после успешного TLS handshake.

Это TCP-транспорт с настоящим TLS, **не реализация браузерного HTTP2/HTTPS**.
Размеры, направления, длительность соединения, RTT и TLS/ALPN остаются
доступными наблюдателю. Потери TCP вызывают head-of-line blocking. Слепое
сравнение с браузерными pcap и испытания в нескольких российских сетях ещё
не проведены. Предыдущую блокировку нельзя приписать конкретному коммиту по
одному совпадению дат; см. `RELEASE_AUDIT_2026-11-08.md`.

## Прямой UDP: отдельный компромисс

Если явно разрешить прямой UDP на обеих сторонах, нужен отдельный случайный
`reality_auth_key` минимум 16 байт, `udp_port`, `enable_udp_data:true`, а на
клиенте ещё `allow_direct_udp:true`. MTU внутреннего пакета — не более 1420.
Это зашифрованный UDP с секретной маской маршрутизации, не QUIC или WebRTC.

Native UDP добавляет зашифрованное двухбайтовое поле длины и ограниченный
padding: до 32 байт для DATA ≤256, до 16 для DATA ≤1024, без дополнительных
случайных байтов для больших DATA. Пустая проба имеет переменный внешний размер
60–188 байт. Пакет IP 1420 байт укладывается в IPv6 MTU 1500 (1498 байт).
Убрана стартовая пачка пяти проб через 50 мс. Recovery-пробы — примерно раз в
7 с ±25%, keepalive — 18 с ±25%; недавний authenticated traffic подавляет
keepalive. К каждому DATA-пакету задержки не добавляются, batching сохраняется.
Настройки сессии UDP публикуются в mux после установки формата, что исключает
гонку с первым входящим пакетом.

## Настройка и совместимость

1. Собрать **оба ядра** с Go 1.27.3 по зафиксированному `go.mod`. Старое ядро
   не поддерживает этот транспорт.
2. `obsidian-server --gen-keys` генерирует внутреннюю пару, независимую REALITY
   X25519 пару и случайный short ID. Приватный транспортный ключ остаётся на
   сервере. Старый HMAC-секрет не заменяет эту пару.
3. Заполнить `examples/server.native-reality.example.json` и
   `examples/client.native-reality.example.json`. Значения `REPLACE_*` —
   обязательные placeholders. Цель должна подходить для upstream REALITY и
   поддерживать TLS 1.3; пример домена не является гарантией пригодности.
4. В приложении новые поля сохраняются через JSON, copyWith, OBSDN и URI.
   Выдача гостевого ключа из импортированного ClientConfig сохраняет их.
   Существующий wizard установки/обновления VPS автоматически новый режим
   не включает: native сервер настраивается отдельно, клиент импортирует ключ.

В URI используются `transport=native-reality`, `rpk`, `rid`, `sni`; разрешение
прямого UDP — `direct_udp=1`. В compact OBSDN соответствуют `tr`, `rpk`, `rid`,
`du`. Старые конфигурации без `transport` сохраняют прежний режим v5. Скрытой
миграции старых серверов нет. В этой работе VPS и опубликованные релизы не
изменялись. В Desktop-репозитории обновлены исходники кодека; установщик Flutter,
APK и IPA не собраны.

## Проверки и скорость

- Windows: **247** Go tests (7 packages), `go vet ./...`, `go mod verify`.
- Пройден настоящий TLS1.3 → внутренний ML-KEM → echo DATA, HTTPS fallback,
  отказ неверного short ID, отмена listener, отказ socket protection,
  немедленное переподключение при смене сети в native и legacy режимах.
- UDP: изменение размеров служебных сообщений, ограничение MTU, batch downlink,
  uplink и authenticated echo, отсутствие передачи control payload в TUN.
- Flutter: **430** tests. Windows client/server и Linux client/server собраны;
  Linux core/client tests выполнены в WSL. Pure-Go пакет клиента компилируется
  для Android arm64, CLI — для macOS arm64. Это не AAR/XCFramework и не runtime
  проверка на телефоне. Race detector и WAN/netem тесты пока не выполнены.

`BenchmarkTunnelRoundTrip`, Windows amd64, Ryzen 5 7600X, Go 1.27.3,
`-benchtime=2s -count=3`, localhost TCP, batch 32×1380, внутренний cipher и
проверка количества доставленных пакетов одинаковы. Handshake не входит в
замер bulk. MB/s — десятичные мегабайты в секунду.

| Транспорт | Три результата MB/s |
| --- | --- |
| Raw TCP (только контроль CPU) | 752.16 / 663.74 / 644.26 |
| Предыдущие записи v5 AEAD | 467.50 / 503.26 / 478.47 |
| Native REALITY TLS | 507.49 / 508.09 / 511.23 |

Первый короткий прогон под параллельной компиляцией давал native 396–515 MB/s;
это показывает чувствительность loopback к нагрузке. Замер не доказывает WAN
скорость, расход батареи, производительность VPS/ARM или качество маскировки.
Следующий критерий выпуска — функциональная полевая проверка и слепая
классификация pcap с известным FPR, как описано в исследовании
`reports/Маскировка и скорость Obsidian.md`. До неё новый режим экспериментальный.

Исходники и лицензии зависимостей перечислены в `THIRD_PARTY_NOTICES.md`.
