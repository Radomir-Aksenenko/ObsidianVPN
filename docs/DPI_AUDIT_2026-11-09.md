# Аудит маскировки Obsidian, 9 ноября 2026

## Область и вывод

Задача — исправить протокол для будущих серверов. Изменения конкретного VPS,
смена адреса, развёртывание и выпуск приложений не входят в эту работу.

**Причина конкретной блокировки ТСПУ не установлена.** Есть воспроизводимые
признаки, по которым прежний протокол можно отличить от HTTPS, и исправления
этих признаков. Это не доказательство того, что РКН применил именно такой
детектор, и не гарантия отсутствия будущих блокировок.

Проверки доступности с рабочего компьютера выполнялись **за пределами России**.
Они подтверждают работоспособность сервера извне и ничего не доказывают о
доступности через российские сети. Конфигурация и процессы VPS не менялись.

## Воспроизводимые недостатки

1. До `dc867ec` после ServerHello шли не TLS-записи. Пассивному анализатору
   достаточно проверить продолжение потока, а не расшифровывать VPN.
2. Старый UDP имеет псевдо-STUN заголовок без полноценного обмена STUN и повторяющийся
   RouteTag. Сегодняшнее удаление STUN и маскирование тега полезны, однако выводить
   маску из публичного server key недостаточно, если наблюдателю известен этот ключ.
3. В новом v4 record mode заголовки `0x17` окружали **незашифрованный BuildHello**.
   В нём виден ML-KEM-768 encapsulation key. Проверка его канонического представления
   через `crypto/mlkem.NewEncapsulationKey768` обнаруживает ключ в старом потоке
   без VPN-секретов. Это воспроизведено в `TestRealityRecordsHideMLKEMHandshake`.
4. Имитация Finished всегда имела длину 53. Для выбранного сайтом прикрытия
   `TLS_AES_256_GCM_SHA384` нужно 69: 4 байта handshake header + 48 verify_data +
   1 inner content type + 16 AEAD tag. Для SHA-256 получается 53.
5. При TLS 1.2/HelloRetryRequest код дописывал искусственную TLS 1.3 flight,
   хотя протокол требует другого продолжения. Ошибки записи encrypted flight
   могли теряться, потому что `sawEncrypted` проверялся раньше ошибки.
6. Автоматический переход records → masked → legacy мог вернуть узнаваемый
   поток после сетевой ошибки. Старый клиент также мог продолжить раскрывать
   отпечаток IP уже после обновления сервера.
7. Клиент отвечал после первой encrypted записи, до получения остальных записей
   flight. При раздельных EncryptedExtensions/Finished это нарушает видимый порядок.

## Исправления в codex/dpi-audit-hardening

- Новый SessionID label `obsidian_reality_v5_records_aead`. Все внутренние байты,
  включая первоначальный ML-KEM обмен, защищаются AES-256-GCM до помещения в TLS-записи.
  HKDF-SHA256 выводит отдельные ключи c2s/s2c из секретного REALITY credential и
  случайного SessionID. Заголовок записи связан с ciphertext через AAD.
- Независимые счётчики направлений; смена SessionID меняет ключи. Повреждение,
  повтор, отражение записи в обратную сторону и перенос в другую сессию отвергаются.
  После первого аутентифицированного record пересинхронизация запрещена.
- До первого своего record допускается только ограниченный 64 KiB хвост настоящей
  cover flight/имитация Finished. Сохраняются handshake deadlines.
- Размер записи: до 16384 внутренних байт + inner type + 16-byte tag. Один batch
  по-прежнему отправляется одним write. Буферы и nonce переиспользуются.
- Ограничение AES-GCM — не более `2^24` записей на направление с одним ключом;
  при достижении требуется новое соединение с новыми ключами.
- Запрещены неявный downgrade клиента и приём raw legacy клиентов сервером.
  Исключения только явные: JSON клиента `reality_legacy_fallback: true`, сервера
  `reality_legacy_clients: true`. Они возвращают старые риски и не рекомендуются.
- Production REALITY требует отдельный секретный `reality_auth_key` от 16 байт;
  рекомендуется 32 случайных байта (64 hex-символа). Подстановка публичного server key
  более не считается безопасным значением по умолчанию.
- UDP route mask в production выведен из этого секретного credential. Сам UDP AEAD,
  O(1) demux, GSO и батчи сохранены.
- Finished выбирается по согласованному cipher suite. TLS 1.2, HRR и недоступная
  цель завершают record-mode соединение без синтетического продолжения.
- Клиент ожидает затишья flight (эвристика 120 мс); это добавляет задержку установки,
  но не задержку на каждый пакет. Это не доказательство полного TLS state-machine.
- Оборванный TLS record не принимается за конец flight. Ошибки/короткие записи
  передаются вызывающему коду; чтение ClientHello ограничено общим deadline,
  а не бесконечно продлеваемым таймером на каждый фрагмент.

## Проверки и производительность

- До изменений: 218 тестов в семи пакетах.
- После изменений: 236 тестов в семи пакетах Windows, `go vet ./...` без ошибок.
- Ядро, клиент и сервер проходят тесты Linux в WSL, включая платформенные UDP GSO
  и socket options. Go-пакеты server/client/mobile кросс-компилируются для Linux amd64.
- Windows race detector не запускался: нет CGO/C-компилятора в Windows-среде.
- `BenchmarkTunnelRoundTrip`, Windows amd64, Ryzen 5 7600X, `-benchtime=2s -count=3`:
  после устранения аллокаций nonce raw 866–994 MB/s, защищённые records 556–689 MB/s;
  по 161 allocs/op в обоих вариантах (op — batch 32×1380 bytes).
  Предыдущая серия: raw 651–676, records 499–528 MB/s. Измерения колеблются;
  дополнительное шифрование снижает CPU throughput примерно на 25–32% по медианам.
  Эти значения не являются скоростью через интернет или результатом на ARM VPS.
- UDP send/receive, предыдущая серия: legacy 182–221 MB/s, masked 204–220 MB/s.
  Диапазоны перекрываются; устойчивого ухудшения этим коротким тестом не установлено.
- Не использована синтетическая модель `tools/tspu_testbed` как доказательство
  неразличимости: её искусственный классификатор не является настоящим ТСПУ.

## Ограничения и следующий этап

Это усиление собственного transport camouflage, **не полноценная реализация
Xray REALITY и не обычное TLS-соединение до cover target**. Оно убирает
подтверждённые детектируемые структуры, но не скрывает IP/SNI, длительность,
распределения размеров/таймингов, характер произвольного UDP, действия клиента
с утёкшими credentials и блокировку подсети целиком. Общий REALITY credential
необходимо держать секретным; компрометация этого PSK раскрывает внешний слой,
хотя внутреннее шифрование VPN остаётся отдельным.

Для выпуска обновлять сначала ядро сервера, затем клиентов; v5 несовместим с
неопубликованным v4 record mode, а strict-клиент не подключится к старому ядру.
Бинарные приложения, сабмодуль приложения, remote-ветки и VPS этой работой не обновлены.

Следующая проверка — реальные захваты v5 и обычного HTTPS, несколько российских
сетей, loss/RTT/MTU и длительный многопользовательский тест. До неё утверждать
«ТСПУ больше не распознаёт протокол» нельзя. Для более сильного свойства стоит
отдельно оценивать переход на сопровождаемый транспорт с настоящей TLS-реализацией.

Основание TLS-размеров и HRR: [RFC 8446](https://www.rfc-editor.org/rfc/rfc8446.html),
разделы 4.1.3, 4.4.4, 5.2, 5.5. Валидатор ключа:
[официальная документация crypto/mlkem](https://pkg.go.dev/crypto/mlkem#NewEncapsulationKey768).
