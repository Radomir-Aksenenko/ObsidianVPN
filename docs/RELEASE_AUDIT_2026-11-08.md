## Проверка того, что действительно опубликовано

Для 2.0.6, 2.0.7 и 2.0.8 скачаны Windows x64 ZIP, Android arm64 APK и unsigned iOS IPA.
Все девять SHA-256 архивов совпали с `digest` GitHub. Проверены вложенные Windows
CLI, Android `libgojni.so`, iOS PacketTunnel и Linux server assets amd64/arm64.

Серверные бинарники одной версии совпали побайтово между тремя контейнерами.
Это исключает расхождение серверного ядра между проверенными Windows/Android/iOS
пакетами. Остальные ABI, Linux/macOS desktop packages и установщик EXE отдельно
не извлекались; их происхождение проверено только по общему workflow.

| 2.0.7 | `b996356c7c484859`… |

Это префиксы хешей для сверки результатов, не полные контрольные суммы.

- 2.0.7: появились masked SessionID и hopping; батчей ещё нет.
- 2.0.8: эти изменения плюс `SendDataBatch`.
- Во всех проверенных версиях отсутствуют ярлыки сегодняшних record modes v4/v5.
- Клиент Windows и оба Linux server assets в nightly **полностью совпали по SHA-256**
  с соответствующими бинарями 2.0.8. Отдельного нового transport fix там нет.

## 2.0.7: что изменилось относительно 2.0.6

1. **SessionID на проводе изменился.** Timestamp замаскирован. По умолчанию это
   улучшает маскировку, но появился селектор masked/legacy.
2. Новый клиент со старым сервером сначала пробует неизвестный тому masked формат.
   Сервер отправляет такую попытку на сайт прикрытия, внутренний handshake не
   проходит, клиент затем пробует legacy. После подтверждённого legacy режима
   новый формат перепроверяется примерно через восемь попыток соединения.
   Это новый источник дополнительных неудачных соединений при смешанных версиях.
3. Исправление UDP port hopping меняет поведение при непустом `port_pool`:
   раньше смена порта ломала connected UDP socket, теперь unconnected socket
   позволяет реально отправлять на другие порты. Следовательно, при включённом
   hopping меняется и наблюдаемая последовательность портов. В прочитанной ранее
   конфигурации проблемного VPS port pool был пустым; это не доказанный триггер
   его блокировки.
4. Mobile Go memory limit поднят с 8 до 24 MiB, GCPercent с 40 до 100;
   UDP socket buffers телефона уменьшены с максимального запроса 16 до 2 MiB.
   Это меняет производительность/очереди, но не алгоритм шифрования пакетов.
5. Сервер получил раздельные адреса клиентов, исправления revocation и освобождения
   handshake slots. Они влияют на стабильность/доступ, но не добавляют TLS-защиту
   сырому потоку. Повреждённый revocation file теперь закрывает вход новым сессиям:
   возможен отказ приложения, но это не объяснение отсутствия TCP SYN на VPS.
6. В оболочке — уведомления об обновлениях и Android CI/cache/ABI build changes.
   Смена SNI/порта сервера или переход с TLS-маскировки на no-TLS в этих diff не найдены.

**Вывод по 2.0.7:** утверждение «ничего сетевого не менялось» неверно. Найденные
изменения не создают новый обязательный постоянный маркер на каждом соединении,
но могут влиять на число попыток и порты. Их вклад в обнаружение не исключён.

## 2.0.8: что изменилось относительно 2.0.7

- TCP autotuning вместо явного SO_RCVBUF/SO_SNDBUF; TCP_NOTSENT_LOWAT 256 KiB;
  настройка и диагностика congestion control, запрос BBR.
- UDP GSO и отправка очереди до 32 пакетов группами.
- TCP `SendDataBatch`, накопление кадров в одном write, buffered reads и
  обновление write deadline раз в секунду.
- Переиспользование UDP scratch buffers и сохранение адреса только при его смене.
- В оболочке — сохранение ключей/серверов после переустановки, Windows updater;
  новые server configs запрашивают 4 MiB UDP buffer и BBR вместо прежнего 16 MiB.

Diff `handshake.go`, `protocol.go`, `crypto.go`, `uri.go`, `go.mod` и `go.sum`
между контрольным core 2.0.6 и core 2.0.8 пустой. Между 2.0.7 и 2.0.8 не изменён
формат REALITY ClientHello/SessionID и сырого продолжения после ServerHello.

**Однако идентичность формата не равна идентичности трафика.** Автоподстройка
окна и GSO/батчи меняют достижимую скорость, группировку/времена пакетов и TCP
сегментацию. Поэтому не исключено, что обновление сделало существующий отпечаток
заметнее для классификатора. Это возможная косвенная связь, не доказанная причина.

## Проверки и границы вывода

- В отдельных чистых worktrees запущены тесты именно старых ядер, без новых v5 fixes:
  `4d87132` (2.0.7) — **197 тестов**, `eacca36` (2.0.8) — **203 теста**, по семь пакетов.
- Проверены исходники тестов батчей и Linux GSO; общий текущий Linux-прогон предыдущего
  аудита покрывал эти пути. Исторические повторные прогоны здесь выполнены в Windows,
  поэтому не выдаются за дополнительный прогон старых Linux-бинарей.
- Функциональные тесты и отсутствие нового явного маркера **не доказывают**
  неразличимость для настоящего ТСПУ.
- Сырые байты после ServerHello и псевдо-STUN уже присутствовали в контрольной 2.0.6
  и сохранялись в 2.0.7/2.0.8. Обновление не «выключило» прежде полноценный TLS:
  полноценной маскировки продолжения потока до этих релизов тоже не было.

## Ответ на вопрос о совпадении

**Нельзя обоснованно назвать блокировку ни доказанной регрессией релиза, ни просто
случайностью.** Подтверждено, что старые признаки обнаружения сохранялись, а релизы
меняли наблюдаемое поведение. Возможны как накопленное/отложенное обнаружение старого
протокола, так и его обнаружение после изменения нагрузки/бурстов/повторных попыток.
Данных для выбора одного механизма нет.

Утверждение «вчерашние релизы точно ни при чём» отзывается как слишком сильное.
Корректнее: **не найдено прямого отключения маскировки, но косвенная связь с
обновлениями остаётся возможной**. Для причинного вывода нужны сравнимые pcap
до/после и сведения о фильтрации из затронутой российской сети. Подмена этого
вывода словом «совпадение» была бы необоснованной.
